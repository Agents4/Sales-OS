# Skill authoring

A skill is a folder with a `SKILL.md` and optional supporting files, following the open Agent Skills format. Sales-OS adds a few conventions so skills work on Gemini, Claude and other agents from one source.

## Where skills live

- `core/skills/<name>/SKILL.md`: the shared product. Changes here ship to every client.
- `local/skills/<name>/SKILL.md`: client-specific skills in an instance. They survive upgrades. A local skill with the same name overrides the core one.
- Never edit `.agents/skills`, `.claude/skills`, `.gemini/commands` or `dist/`. They are generated by `python3 tools/sos.py build`.

## Naming

- Lowercase letters, digits, single hyphens. 64 characters at most. The folder name equals `name`.
- `mh-` for methodology skills, `sos-` for system skills. Client skills choose their own prefix.
- The slash command is the name without the prefix (`mh-blue-sheet` becomes `/sos:blue-sheet`). Two skills may not produce the same command.

## Frontmatter

```
---
name: mh-example
description: "What it does. Use when ... (trigger words the user would say)."
compatibility: "One line on what it needs; say what happens without it."
metadata:
  version: "1.0.0"
  layer: methodology
  last_reviewed: "2026-10-17"
  includes: "templates/blue-sheet.md, shared/operating-rules.md"
---
```

- The `description` decides whether the skill is chosen. Say what it does and when to use it, with the words a seller would use. Under 1,024 characters.
- Only these keys are allowed at top level: `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`. Metadata values are strings.
- `includes` lists files relative to `core/` that are copied into the compiled skill: templates go to `assets/`, everything else to `references/`. Every compiled skill is self-contained, which is what the Gemini app needs (skills are uploaded as zip files).
- Reference included files in the body as `references/<file>` or `assets/<file>`. Validation fails if the body refers to a file that is not included, and warns if an included file is never mentioned.

## Body structure

Use these sections, in this order:

1. A two-sentence purpose.
2. `## When to use` with trigger situations and a "Not for" line.
3. `## Inputs`.
4. `## Procedure` as numbered steps. Imperative, specific, in the order of work.
5. `## Output` stating file locations (with file access) and the chat-only form.
6. `## Quality gate` with checks the agent must run before finishing.

Keep the body under 500 lines and the whole file near 5,000 words at most. Put detail in included references.

## Writing rules

- Say what to do, not what to avoid, except for hard rules.
- Be explicit about the evidence rule: never invent, tag F/I/A/U, cite sources.
- Always state the internal versus buyer-facing boundary for anything a buyer could see.
- Add approval gates for every outward action.
- Make capability checks explicit: what to do with and without files, shell, web, Google, CRM, subagents.
- No scripts inside skills. Anything that needs code lives in `tools/` and is called from the skill only when a shell exists, with a manual fallback.
- Do not rely on network access from scripts.

## Test

1. `python3 tools/sos.py validate`. Fix errors, then warnings.
2. Run the skill on an eval case from `evals/cases/` and score it with `evals/rubric.md`. Add a case for any new behavior.
3. `python3 tools/sos.py build` then `python3 tools/sos.py build --check` to confirm generated outputs match.
4. Try it on a second platform (for example the Gemini app with the zip) to see the self-contained version work.

## Ship

Bump `metadata.version`, update `last_reviewed`, add a line to `CHANGELOG.md`, add the skill to a bundle in `core/bundles.json`, and run the release command.
